## Define the recovery objective

A backup becomes useful when you can restore it. This exercise uses PostgreSQL 18, synthetic data and a disposable container. It tests logical backups, not physical recovery or point-in-time recovery. The [import/export guide](/postgresql/inserting-and-modifying-data/importing-and-exporting-data-in-postgresql) explains the two restore formats, and [backup considerations](/managing-databases/backup-considerations) explains their place in a recovery plan.

For this lab, the recovery point objective is to retain every row present at the dump's snapshot. Writes made after that snapshot are deliberately outside the guarantee. The recovery time measurement starts before restoring into an already-created empty destination and stops after validation. It excludes provision time and depends on this small fixture's size and your machine. Measure your own result; this exercise does not predict production recovery times.

## Run the disposable exercise

The repository's tutorial runner creates a uniquely named container from an immutable PostgreSQL image, binds only to loopback, loads synthetic data, restores into separate empty databases and removes the container in a `finally` block. It uses no cloud account or production credentials. From a checkout of the Data Guide with Docker and Node.js 22.18.0 or later:

```bash
npm run test:tutorials
```

The runner is `tests/tutorials/run.mjs` in [the Data Guide repository](https://github.com/prisma/dataguide). It saves actual version, source hashes, check results, elapsed restore time and cleanup status in `.verification-runs/postgresql.json`. CI retains this as an artifact; a failed check fails the job.

## What the exercise checks

The source database has an identity primary key, a required unique label and an ordinary OID-valued column. A plain dump is restored with `psql -X -v ON_ERROR_STOP=1`; a custom archive is restored with `pg_restore --exit-on-error`. Both destinations must preserve the row and OID value, generate the next identity value, and reject both a duplicate label and an explicit NULL. These checks exercise schema, data, constraints and sequence state together.

The failure control feeds invalid SQL into a third destination. The restore must return a failing process status and must not create the table after the invalid statement. Earlier statements may have committed: fail-fast execution alone is not atomic rollback. Use a single transaction only when the dump's statements support it.

The application smoke test reads the restored row and inserts another row under a restricted application role. This proves the tested permissions and invariants for this fixture; it does not replace your application's own smoke tests.

## Interpret the recovery result

The report records elapsed restoration and validation time separately from the snapshot's recovery point. A row written after the dump is absent from the restore, demonstrating the boundary of a logical snapshot. In a real drill, also verify extensions, role ownership, application permissions, collation requirements and all business invariants. Keep the recovery destination isolated until these checks pass, then follow an approved cutover plan.

Cleanup is part of the exercise. A successful report requires container removal. Backup files and real restored data would also need the same access and retention controls as the original data; this fixture contains only synthetic values.
